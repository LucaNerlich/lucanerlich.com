# Mermaid Diagrams Guide

[Mermaid](https://mermaid.js.org/) renders a diagram from a plain-text definition inside a Markdown code
block. You describe the picture next to the prose. There is no exported image to keep in sync.

The examples below are the working set for **this site**. They use syntax that Mermaid 12 accepts in the
Docusaurus theme configured here. Copy the `markdown` block under each diagram. The
[live editor](https://mermaid.live/) is useful for drafting, and it can be a different Mermaid release
than the one that publishes this page. Theme, dark mode, and what `pnpm build` does not check are in
[Mermaid in Docusaurus](#mermaid-in-docusaurus).

## Getting Started

In Docusaurus, you create a Mermaid diagram with a fenced code block using the `mermaid` language
identifier:

````markdown
```mermaid
flowchart LR
    A --> B --> C
```
````

This renders as:

```mermaid
flowchart LR
    A --> B --> C
```

A line that starts with `%%` is a comment. Mermaid drops it before parsing.

:::tip
Mermaid diagrams are **text-based and version-controlled**. They live alongside your documentation in Git,
making them easy to review, diff, and update. No external image files needed.
:::

## Flowcharts

Flowcharts are the most common diagram type. They show processes, decisions, and directional flows.

### Direction

The first keyword sets the layout direction. `flowchart` is the current keyword. `graph` is the older
alias and still renders -- both go through the same parser. Prefer `flowchart` in new diagrams. If you
omit the direction, Mermaid lays the chart out top to bottom.

| Keyword | Direction |
|---------|-----------|
| `flowchart TD` or `flowchart TB` | Top to bottom |
| `flowchart BT` | Bottom to top |
| `flowchart LR` | Left to right |
| `flowchart RL` | Right to left |

### Basic flowchart

```mermaid
graph TD
    Start([Start]) --> Input[/User enters data/]
    Input --> Validate{Is data valid?}
    Validate -->|Yes| Process[Process data]
    Validate -->|No| Error[Show error message]
    Error --> Input
    Process --> Store[(Save to database)]
    Store --> Done([End])
```

        direction LR

        direction LR
        Handler[Handler] --> DB[(DB)]

## Sequence Diagrams

Sequence diagrams show interactions between participants (systems, services, users) over time.

### Basic sequence

```mermaid
sequenceDiagram
    participant User
    participant Browser
    participant Server
    participant DB as Database

    User->>Browser: Click "Login"
    Browser->>Server: POST /api/login
    Server->>DB: SELECT user WHERE email=?
    DB-->>Server: User record
    Server-->>Browser: 200 OK + JWT token
    Browser-->>User: Show dashboard
```

### Arrow types

| Syntax | Style |
|--------|-------|
| `->>` | Solid message arrow |
| `-->>` | Dashed message arrow, commonly used for replies |
| `-x` | Solid with cross (lost message) |
| `--x` | Dashed with cross |
| `-)` | Solid with open arrow (async) |
| `--)` | Dashed with open arrow |

### Numbers, options, and parallel work

`autonumber` prefixes each message with a step number. `opt` is an optional block. `alt` / `else`,
used in the cache example below, is the branch. `par` / `and` draw messages side by side. `actor`
draws a person and `participant` draws a box. `box` only groups them on the diagram -- message order
is still top to bottom.

```mermaid
sequenceDiagram
    autonumber
    box rgb(240, 248, 255) Client
        actor User
        participant App
    end
    participant API

    User->>App: Open page
    opt Cached session
        App-->>User: Render cache
    end
    par Load
        App->>API: GET /session
    and
        App->>API: GET /flags
    end
```

## Class Diagrams

Class diagrams show the structure of a system: classes, attributes, methods, and relationships.

### Basic class diagram

```mermaid
classDiagram
    class Animal {
        +String name
        +int age
        +makeSound() void
        +move() void
    }

    class Dog {
        +String breed
        +fetch() void
        +makeSound() void
    }

    class Cat {
        +boolean isIndoor
        +purr() void
        +makeSound() void
    }

    Animal <|-- Dog : extends
    Animal <|-- Cat : extends
```

### Visibility modifiers

| Prefix | Meaning |
|--------|---------|
| `+` | Public |
| `-` | Private |
| `#` | Protected |
| `~` | Package/internal |

### Relationship types

```mermaid
classDiagram
    classA --|> classB : Inheritance
    classC --* classD : Composition
    classE --o classF : Aggregation
    classG --> classH : Association
    classI ..> classJ : Dependency
    classK ..|> classL : Realization
```

Source:

````markdown
```mermaid
classDiagram
    classA --|> classB : Inheritance
    classC --* classD : Composition
    classE --o classF : Aggregation
    classG --> classH : Association
    classI ..> classJ : Dependency
    classK ..|> classL : Realization
```
````

| Syntax | Relationship |
|--------|-------------|
| `<\|--` or `--\|>` | Inheritance (extends) |
| `*--` or `--*` | Composition (owns, lifecycle-bound) |
| `o--` or `--o` | Aggregation (has, independent lifecycle) |
| `-->` | Association (uses) |
| `..>` | Dependency (depends on) |
| `<\|..` or `..\|>` | Realization (implements) |

The arrowhead sits on the parent or the interface, so `<|--` and `--|>` are the same relation written
in opposite directions. A single dash does not parse: `classA -|> classB`, `classC -* classD`, and
`classE -o classF` all fail. Use two dashes, as in the diagram above.

### Practical example: repository pattern

```mermaid
classDiagram
    class UserRepository {
        <<interface>>
        +findById(id: String) User
        +findAll() List~User~
        +save(user: User) User
        +delete(id: String) void
    }

    class JpaUserRepository {
        -EntityManager em
        +findById(id: String) User
        +findAll() List~User~
        +save(user: User) User
        +delete(id: String) void
    }

    class UserService {
        -UserRepository repo
        +getUser(id: String) UserDTO
        +createUser(dto: CreateUserDTO) UserDTO
    }

    class User {
        +String id
        +String email
        +String name
        +LocalDateTime createdAt
    }

    UserRepository <|.. JpaUserRepository
    UserService --> UserRepository
    JpaUserRepository --> User
```

### Relationship cardinality

| Syntax | Meaning |
|--------|---------|
| `\|\|--\|\|` | One to one |
| `\|\|--o{` | One to many |
| `o{--o{` | Many to many |

| Symbol | Meaning |

| `\|{` | One or more |

## Architecture Diagrams

An architecture diagram draws services inside groups and connects a side of one service to a side of
another. Built-in icons on this Mermaid build are `cloud`, `database`, `disk`, `internet`, `server`,
and `blank`. The first word of the block is `architecture-beta`.

Sides are `L`, `R`, `T`, and `B`. `reader:R -- L:pages` draws an edge from the right of `reader` to
the left of `pages`.

```mermaid
architecture-beta
    group site(cloud)[Docs site]

    service pages(server)[Docusaurus] in site
    service diagrams(disk)[Mermaid] in site

    service reader(internet)[Reader]

    reader:R -- L:pages
    pages:B -- T:diagrams
```

## Tips and Best Practices

### Keep diagrams focused

A diagram that tries to show everything shows nothing. Each diagram should communicate **one idea**.
If your flowchart has more than 15-20 nodes, consider splitting it into multiple diagrams.

### Use meaningful node IDs

```text
# Hard to read
A --> B --> C --> D

# Self-documenting
Request --> Validate --> Process --> Respond
```

### Use aliases for long participant names

```mermaid
sequenceDiagram
    participant FE as Frontend App
    participant GW as API Gateway
    participant Auth as Auth Service
    participant DB as PostgreSQL

    FE->>GW: Request
    GW->>Auth: Validate token
    Auth-->>GW: Valid
    GW->>DB: Query
    DB-->>GW: Results
    GW-->>FE: Response
```

Source:

````markdown
```mermaid
sequenceDiagram
    participant FE as Frontend App
    participant GW as API Gateway
    participant Auth as Auth Service
    participant DB as PostgreSQL

    FE->>GW: Request
    GW->>Auth: Validate token
    Auth-->>GW: Valid
    GW->>DB: Query
    DB-->>GW: Results
    GW-->>FE: Response
```
````

### Quote labels that contain shape characters

Parentheses, brackets, braces, and pipes are shape syntax. In an unquoted node label they end the
node, and the diagram fails to parse. Put that label in double quotes:

```text
A["Process (main)"]
B["Use {id}"]
C["a | b"]
D["arr[0]"]
```

An edge label follows the same rule. `A -->|O(n)| B` fails. This works:

```text
A -->|"O(n) complexity"| B
```

A colon, hash, ampersand, or slash inside a node label does not need quotes: `A[Step 1: Initialize]`.
A unicode arrow is not a Mermaid edge. `A —> B` and `A → B` are lexical errors. The edge is three
ASCII characters: `-->`.

### Avoid common mistakes

| Mistake | What happens | Fix |
|---------|--------------|-----|
| Spaces in a node ID | Parse error | `userInput` or `user_input` |
| `end` as a node ID | `end` closes a subgraph, `alt`, `loop`, or `par` | `endNode` or `done` |
| One dash in a class relation | `-|>`, `-*`, and `-o` do not parse | `--|>`, `--*`, `--o` |
| Unquoted shape characters in a label | `()`, `[]`, `{}`, or a pipe ends the node | Double quotes around the label |
| `%%{init}%%` that sets `theme` | That diagram ignores the light/dark toggle | Leave the theme to the site config |
| `click node callback` | Ignored. `securityLevel` is `strict` and a diagram cannot lower it | Link from the prose instead |
| Omitting `TB` or `LR` | The flowchart defaults to top to bottom | Set the direction when it matters |
| Very long labels | The diagram becomes unreadable | Short labels, detail in the prose |
| Too many nodes | Visual clutter | Split into more than one diagram |

### Check the renderer that publishes the page

The live editor is a draft tool. Mermaid versions, enabled diagram types, and security settings differ
between this site, GitHub, GitLab, and editor extensions. Keep each diagram and the `markdown` source
under it identical.

```bash
pnpm build
```

`pnpm build` compiles the page. It does not parse Mermaid, and it does not parse the `markdown`
source fences that show the copy-paste text. A bad diagram still builds. Open the page: the theme
renders in the browser, and a syntax error shows up in the diagram's error boundary. Check light and
dark.

### Make diagrams accessible

Do not make a diagram the sole way to convey important information. Introduce it with a useful heading,
explain the conclusion in nearby prose, and give dense diagrams a caption or a short text alternative.
Use meaningful labels instead of anonymous node IDs, keep color from being the only signal, and check both
light and dark themes. Mermaid supports accessibility directives for diagram types that implement them:

```mermaid
flowchart LR
    accTitle: Sign-in request flow
    accDescr: The browser submits credentials to the application, which validates them and returns a session.
    Browser --> Application --> Session
```

````markdown
```mermaid
flowchart LR
    accTitle: Sign-in request flow
    accDescr: The browser submits credentials to the application, which validates them and returns a session.
    Browser --> Application --> Session
```
````

For diagrams with operational or security meaning, add a textual sequence or table as well. This also makes
the content searchable and understandable when SVG rendering is unavailable.

### Treat diagram input as untrusted

Do not interpolate user-controlled text into a Mermaid definition. This site keeps `securityLevel` at
`strict`, which sanitizes HTML in labels and ignores `click` callbacks. Do not loosen that in
`themeConfig.mermaid.options` without a reviewed reason. If application data must become a diagram,
validate and escape it first, and render it in the same environment in which users will view it.

## Mermaid in Docusaurus

Three settings in `docusaurus.config.ts` turn diagrams on:

```typescript
const config = {
    markdown: {
        mermaid: true,
    },
    themes: ['@docusaurus/theme-mermaid'],
    themeConfig: {
        mermaid: {
            theme: {light: 'default', dark: 'dark'},
        },
    },
};
```

`markdown.mermaid` tells the MDX loader to turn a code fence whose language is `mermaid` into a
diagram. The language has to be exactly that word. A title or a highlight range on the fence is
ignored: the block still renders, and the title does not appear.

`@docusaurus/theme-mermaid` 3.10 draws each diagram in the browser. It depends on `mermaid`
`>= 11.6.0`. This repo currently resolves Mermaid 12.0.0. The lockfile is the source of truth for
the version -- the live editor and a GitHub preview can be a different release.

The theme calls `mermaid.initialize` with `startOnLoad: false` and the theme for the active color
mode. Light mode uses Mermaid's `default` theme. Dark mode uses `dark`. The site default is dark,
and the color mode follows the system preference, so a diagram is drawn for the mode the reader
ends up with. Toggling color mode draws it again. `themeConfig.mermaid.options` is empty, so the
rest of Mermaid's defaults apply:

| Default | Value here | What it means |
|---------|------------|---------------|
| `securityLevel` | `strict` | HTML in labels is sanitized. `click` callbacks are ignored. A diagram cannot lower this with an `init` directive. |
| `htmlLabels` | `true` | A label may contain `<br/>` for a line break. Other HTML is stripped. |
| `look` | `classic` | The classic node style. This site does not set `look`. |
| `layout` | `elk` | Flowcharts use the ELK layout bundled with Mermaid 12. You do not need `@mermaid-js/layout-elk`. |
| `gitGraph.mainBranchName` | `main` | The first commits in a git graph sit on `main`. |

`securityLevel`, `startOnLoad`, `maxTextSize`, `suppressErrorRendering`, and `maxEdges` are locked.
An `%%{init}%%` block can still set `theme`, `look`, or `layout` for that one diagram. An init theme
stays put after the reader switches to dark mode. Leave it out unless you have checked both color
modes.

`classDef` fill and stroke colors are literal CSS. They do not follow the toggle. Prefer the theme
colors, and put the meaning in the label when color would otherwise be the only signal.

Diagrams are wrapped in `.docusaurus-mermaid-container`. `useMaxWidth` defaults to true, so the SVG
scales down to the column. A wide chart becomes unreadably small. Split it instead of overriding
layout for the whole site.

### Where Mermaid works

| Platform | Support |
|----------|---------|
| Docusaurus (with theme) | This site's configured renderer |
| GitHub Markdown | Native Mermaid rendering; supported syntax can differ from this site |
| GitLab Markdown | Native rendering on supported GitLab versions; verify the instance configuration |
| Notion | No equivalent built-in Mermaid code-block renderer; use an integration or an exported image |
| VS Code | Via an extension, whose Mermaid version and settings determine support |
| Confluence | Via an installed app/plugin |

### Diagram types not given a full example

Mermaid 12 also registers `block` / `block-beta`, C4 (`C4Context`, `C4Container`, `C4Component`,
`C4Dynamic`, `C4Deployment`), `sankey` / `sankey-beta`, `requirement` / `requirementDiagram`,
`kanban`, `packet` / `packet-beta`, and beta diagrams such as `radar-beta`, `treemap`,
`ishikawa`, `venn-beta`, `wardley-beta`, and `usecase-beta`. The keyword has to be the first word
of the block. Syntax for the beta types moves between minor releases. Render one on this site
before you standardize on it. The
[syntax reference](https://mermaid.js.org/intro/syntax-reference.html) is the catalog; this page is
the set that already renders here.

### Responsive diagrams

Wide diagrams are hard to read on a phone. Several focused diagrams beat one dense canvas. Use short
labels, and look at the page at a narrow width before you publish it.

### Live editor

Draft in the [Mermaid Live Editor](https://mermaid.live/), then paste the definition here and read
the page in both color modes. Export to SVG or PNG only when the destination has no Mermaid renderer.
