# Mermaid Diagrams Guide

[Mermaid](https://mermaid.js.org/) describes a diagram as plain text inside a Markdown code block.
You describe the picture next to the prose. There is no exported image to keep in sync.

The examples below are the working set for **this site**. They use the syntax that Pele, the renderer
here, accepts in the Mermaid 12.1 language. Copy the `markdown` block under each diagram. The
[live editor](https://mermaid.live/) is useful for drafting, but it draws with Mermaid, not Pele, so
spacing and layout differ. Rendering, theming, and the build checks are in
[How this site renders Mermaid](#how-this-site-renders-mermaid). To ship the same renderer in an
application, see [Using Pele in your app](#using-pele-in-your-app).

## Getting Started

In Docusaurus, you create a Mermaid diagram with a fenced code block using the `mermaid` language
identifier:

````markdown
```mermaid
flowchart LR
    A --> B --> C
```
````

This renders as:

```mermaid
flowchart LR
    A --> B --> C
```

A line that starts with `%%` is a comment. Mermaid drops it before parsing.

:::tip
Mermaid diagrams are **text-based and version-controlled**. They live alongside your documentation in Git,
making them easy to review, diff, and update. No external image files needed.
:::

## Flowcharts

Flowcharts are the most common diagram type. They show processes, decisions, and directional flows.

### Direction

The first keyword sets the layout direction. `flowchart` is the current keyword. `graph` is the older
alias and still renders - both go through the same parser. Prefer `flowchart` in new diagrams. If you
omit the direction, Mermaid lays the chart out top to bottom.

| Keyword | Direction |
|---------|-----------|
| `flowchart TD` or `flowchart TB` | Top to bottom |
| `flowchart BT` | Bottom to top |
| `flowchart LR` | Left to right |
| `flowchart RL` | Right to left |

### Basic flowchart

```mermaid
graph TD
    Start([Start]) --> Input[/User enters data/]
    Input --> Validate{Is data valid?}
    Validate -->|Yes| Process[Process data]
    Validate -->|No| Error[Show error message]
    Error --> Input
    Process --> Store[(Save to database)]
    Store --> Done([End])
```

## Sequence Diagrams

Sequence diagrams show interactions between participants (systems, services, users) over time.

### Basic sequence

```mermaid
sequenceDiagram
    participant User
    participant Browser
    participant Server
    participant DB as Database

    User->>Browser: Click "Login"
    Browser->>Server: POST /api/login
    Server->>DB: SELECT user WHERE email=?
    DB-->>Server: User record
    Server-->>Browser: 200 OK + JWT token
    Browser-->>User: Show dashboard
```

### Arrow types

| Syntax | Style |
|--------|-------|
| `->>` | Solid message arrow |
| `-->>` | Dashed message arrow, commonly used for replies |
| `-x` | Solid with cross (lost message) |
| `--x` | Dashed with cross |
| `-)` | Solid with open arrow (async) |
| `--)` | Dashed with open arrow |

### Numbers, options, and parallel work

`autonumber` prefixes each message with a step number. `opt` is an optional block. `alt` / `else`,
used in the cache example below, is the branch. `par` / `and` draw messages side by side. `actor`
draws a person and `participant` draws a box. `box` only groups them on the diagram - message order
is still top to bottom.

```mermaid
sequenceDiagram
    autonumber
    box rgb(240, 248, 255) Client
        actor User
        participant App
    end
    participant API

    User->>App: Open page
    opt Cached session
        App-->>User: Render cache
    end
    par Load
        App->>API: GET /session
    and
        App->>API: GET /flags
    end
```

## Class Diagrams

Class diagrams show the structure of a system: classes, attributes, methods, and relationships.

### Basic class diagram

```mermaid
classDiagram
    class Animal {
        +String name
        +int age
        +makeSound() void
        +move() void
    }

    class Dog {
        +String breed
        +fetch() void
        +makeSound() void
    }

    class Cat {
        +boolean isIndoor
        +purr() void
        +makeSound() void
    }

    Animal <|-- Dog : extends
    Animal <|-- Cat : extends
```

### Visibility modifiers

| Prefix | Meaning |
|--------|---------|
| `+` | Public |
| `-` | Private |
| `#` | Protected |
| `~` | Package/internal |

### Relationship types

```mermaid
classDiagram
    classA --|> classB : Inheritance
    classC --* classD : Composition
    classE --o classF : Aggregation
    classG --> classH : Association
    classI ..> classJ : Dependency
    classK ..|> classL : Realization
```

Source:

````markdown
```mermaid
classDiagram
    classA --|> classB : Inheritance
    classC --* classD : Composition
    classE --o classF : Aggregation
    classG --> classH : Association
    classI ..> classJ : Dependency
    classK ..|> classL : Realization
```
````

| Syntax | Relationship |
|--------|-------------|
| `<\|--` or `--\|>` | Inheritance (extends) |
| `*--` or `--*` | Composition (owns, lifecycle-bound) |
| `o--` or `--o` | Aggregation (has, independent lifecycle) |
| `-->` | Association (uses) |
| `..>` | Dependency (depends on) |
| `<\|..` or `..\|>` | Realization (implements) |

The arrowhead sits on the parent or the interface, so `<|--` and `--|>` are the same relation written
in opposite directions. A single dash does not parse: `classA -|> classB`, `classC -* classD`, and
`classE -o classF` all fail. Use two dashes, as in the diagram above.

### Practical example: repository pattern

```mermaid
classDiagram
    class UserRepository {
        <<interface>>
        +findById(id: String) User
        +findAll() List~User~
        +save(user: User) User
        +delete(id: String) void
    }

    class JpaUserRepository {
        -EntityManager em
        +findById(id: String) User
        +findAll() List~User~
        +save(user: User) User
        +delete(id: String) void
    }

    class UserService {
        -UserRepository repo
        +getUser(id: String) UserDTO
        +createUser(dto: CreateUserDTO) UserDTO
    }

    class User {
        +String id
        +String email
        +String name
        +LocalDateTime createdAt
    }

    UserRepository <|.. JpaUserRepository
    UserService --> UserRepository
    JpaUserRepository --> User
```

| Syntax | Meaning |
|--------|---------|

| `\|{` | One or more |

## Architecture Diagrams

An architecture diagram draws services inside groups and connects a side of one service to a side of
another. Built-in icons on this Mermaid build are `cloud`, `database`, `disk`, `internet`, `server`,
and `blank`. The first word of the block is `architecture-beta`.

Sides are `L`, `R`, `T`, and `B`. `reader:R -- L:pages` draws an edge from the right of `reader` to
the left of `pages`.

```mermaid
architecture-beta
    group site(cloud)[Docs site]

    service pages(server)[Docusaurus] in site
    service diagrams(disk)[Mermaid] in site

    service reader(internet)[Reader]

    reader:R -- L:pages
    pages:B -- T:diagrams
```

## Gantt Charts

Gantt charts visualize project timelines, task durations, and dependencies.

```mermaid
gantt
    title Project Timeline
    dateFormat YYYY-MM-DD
    excludes weekends

    section Planning
        Requirements           :done,    req,  2025-01-06, 5d
        Architecture design    :done,    arch, after req,   3d
        Technical review       :done,    rev,  after arch,  2d

    section Development
        Backend API            :active,  api,  after rev,   10d
        Frontend UI            :active,  ui,   after rev,   12d
```

## Tips and Best Practices

### Keep diagrams focused

A diagram that tries to show everything shows nothing. Each diagram should communicate **one idea**.
If your flowchart has more than 15-20 nodes, consider splitting it into multiple diagrams.

### Use meaningful node IDs

```text
# Hard to read
A --> B --> C --> D

# Self-documenting
Request --> Validate --> Process --> Respond
```

### Use aliases for long participant names

```mermaid
sequenceDiagram
    participant FE as Frontend App
    participant GW as API Gateway
    participant Auth as Auth Service
    participant DB as PostgreSQL

    FE->>GW: Request
    GW->>Auth: Validate token
    Auth-->>GW: Valid
    GW->>DB: Query
    DB-->>GW: Results
    GW-->>FE: Response
```

Source:

````markdown
```mermaid
sequenceDiagram
    participant FE as Frontend App
    participant GW as API Gateway
    participant Auth as Auth Service
    participant DB as PostgreSQL

    FE->>GW: Request
    GW->>Auth: Validate token
    Auth-->>GW: Valid
    GW->>DB: Query
    DB-->>GW: Results
    GW-->>FE: Response
```
````

### Quote labels that contain shape characters

Parentheses, brackets, braces, and pipes are shape syntax. In an unquoted node label they end the
node, and the diagram fails to parse. Put that label in double quotes:

```text
A["Process (main)"]
B["Use {id}"]
C["a | b"]
D["arr[0]"]
```

An edge label follows the same rule. `A -->|O(n)| B` fails. This works:

```text
A -->|"O(n) complexity"| B
```

A colon, hash, ampersand, or slash inside a node label does not need quotes: `A[Step 1: Initialize]`.
A unicode arrow is not a Mermaid edge. `A —> B` and `A → B` are lexical errors. The edge is three
ASCII characters: `-->`.

### Avoid common mistakes

| Mistake | What happens | Fix |
|---------|--------------|-----|
| Spaces in a node ID | Parse error | `userInput` or `user_input` |
| `end` as a node ID | `end` closes a subgraph, `alt`, `loop`, or `par` | `endNode` or `done` |
| One dash in a class relation | `-|>`, `-*`, and `-o` do not parse | `--|>`, `--*`, `--o` |
| Unquoted shape characters in a label | `()`, `[]`, `{}`, or a pipe ends the node | Double quotes around the label |
| `%%{init}%%` that sets `theme` | Pele takes its colors from the site stylesheet, so an init theme has no effect | Leave the theme to `src/css/custom.css` |
| `click node callback` | Ignored. Pele renders `click node "https://..."` links only | Link from the prose instead |
| HTML in a label | Labels are SVG text: line breaks, bold, and italic render, other tags show as text | Keep labels plain |
| Omitting `TB` or `LR` | The flowchart defaults to top to bottom | Set the direction when it matters |
| Very long labels | The diagram becomes unreadable | Short labels, detail in the prose |
| Too many nodes | Visual clutter | Split into more than one diagram |

### Check the renderer that publishes the page

The live editor is a draft tool. Mermaid versions, enabled diagram types, and security settings differ
between this site, GitHub, GitLab, and editor extensions. Keep each diagram and the `markdown` source
under it identical.

```bash
pnpm build
```

`pnpm build` draws every diagram with Pele. A diagram that does not parse stops the build and names
the file and the line:

```text
docs/example.mdx:42: invalid Mermaid diagram (syntax)
...
```

```bash
pnpm test
```

`pnpm test` renders the `markdown` fences that hold the copy-paste text as well, so a broken example
fails CI too. Neither command tells you how a diagram looks: open the page, and check light and dark.

### Make diagrams accessible

Do not make a diagram the sole way to convey important information. Introduce it with a useful heading,
explain the conclusion in nearby prose, and give dense diagrams a caption or a short text alternative.
Use meaningful labels instead of anonymous node IDs, keep color from being the only signal, and check both
light and dark themes. Pele turns `accTitle` and `accDescr` into the SVG's `title`, `desc`, and ARIA
references, and gives every diagram on a page its own ids:

```mermaid
flowchart LR
    accTitle: Sign-in request flow
    accDescr: The browser submits credentials to the application, which validates them and returns a session.
    Browser --> Application --> Session
```

````markdown
```mermaid
flowchart LR
    accTitle: Sign-in request flow
    accDescr: The browser submits credentials to the application, which validates them and returns a session.
    Browser --> Application --> Session
```
````

For diagrams with operational or security meaning, add a textual sequence or table as well. This also makes
the content searchable and understandable when SVG rendering is unavailable. A diagram that offers zoom
is reachable by keyboard: tab to it, then use `+`, `-`, `0`, and the arrow keys.

### Treat diagram input as untrusted

Diagrams are part of the site, not reader input: Pele draws them at build time and the page ships the
resulting SVG. Do not interpolate user-controlled text into a diagram definition. Pele escapes label
text, never turns diagram source into scripts, event handlers, or HTML labels, filters links to `http`,
`https`, `mailto`, and `tel`, and ignores JavaScript callbacks in `click` statements. Error messages can
quote the diagram source, so keep them in the build log rather than showing them to readers. If
application data must become a diagram, validate and escape it first, and review the page after the
build.

## Using Pele in your app

[Pele](https://github.com/obsidianmd/pele) is Obsidian's open-source Mermaid renderer. It turns Mermaid
source into SVG: small, synchronous, no runtime dependencies, and themed with CSS variables. It targets
Mermaid 12.1 syntax with its own layout engine, so the picture will not match `mermaid.js` pixel for
pixel - the language is the same; the drawing is Pele's.

Use it when you want diagrams in a product without shipping Mermaid's browser stack: build-time docs,
server-rendered pages, or a client that inserts SVG and lets CSS handle light and dark. Docs and a
playground live at [pele.run](https://pele.run/); the source is on
[GitHub](https://github.com/obsidianmd/pele).

### Install

```bash
npm install pele
```

Or load the browser build from a CDN ([API: using a CDN](https://pele.run/api#using-a-cdn)):

```html
<script src="https://cdn.jsdelivr.net/npm/pele@1/dist/pele.global.js"></script>
<script>
  for (const el of document.querySelectorAll('pre.mermaid')) {
    pele.mount(el, el.textContent);
  }
</script>
```

`@1` tracks the latest 1.x release. Pin an exact version when you need a fixed draw.

### Render flow

Two entry points cover most apps:

1. **`render(source)`** - returns `{ svg, width, height, type, ... }`. Insert the SVG yourself. Works
   in Node and in the browser. Throws `PeleError` on bad input.
2. **`mount(element, text)`** - draws into a DOM node, measures fonts from CSS, treats the container
   width as `maxWidth`, and re-lays out on resize. Prefer this for live, editable, or responsive UI.

Minimal client path:

```typescript
import {render} from 'pele';

const {svg} = render(`flowchart LR
  A[Mermaid text] --> B[SVG]`);

document.querySelector('#diagram').innerHTML = svg;
```

Live container:

```typescript
import {mount} from 'pele';

const diagram = mount(document.querySelector('#diagram'), source);
diagram.update('flowchart LR\n  A[Draft] --> B[Published]');
```

`mount()` does not throw on a bad diagram: the container shows the error (dimmed previous SVG, or in
place if nothing drew yet). Read it from `diagram.error`, or pass `onError`. Always display
`PeleError.message` with `textContent` - the message can include diagram source.

Catch failures from `render()` the same way this site's remark plugin does:

```typescript
import {PeleError, render} from 'pele';

try {
    container.innerHTML = render(source).svg;
} catch (error) {
    if (!(error instanceof PeleError)) {
        throw error;
    }
    container.textContent = error.message;
}
```

Useful options on `render` / `mount` (all optional; full list on the [API page](https://pele.run/api)):

| Option | Role |
|--------|------|
| `fontFamily`, `fontSize` | Label font; defaults `sans-serif` / `16` |
| `idPrefix` | Unique prefix for SVG ids when several diagrams share a page |
| `maxWidth` | Available width in px; Pele may wrap labels or rearrange |
| `autoDirection` | Below the breakpoint, some diagrams may flip to a vertical layout |
| `linkSchemes` | Allowed link schemes; default `http`, `https`, `mailto`, `tel` |

Theme with `--pele-*` CSS variables on `.pele` or a parent. Colors follow the theme toggle without a
redraw - see [Theming](https://pele.run/theming).

### Smaller bundles

The default `pele` import registers every Mermaid 12.1 diagram type. Trim the initial load when you
only need a few:

```typescript
import {register, render} from 'pele/core';
import flowchart from 'pele/diagrams/flowchart';
import sequence from 'pele/diagrams/sequence';

register(flowchart, sequence);
const {svg} = render(source);
```

Or load types on first use:

```typescript
import {renderAsync} from 'pele/lazy';

const {svg} = await renderAsync(source);
```

### How this site uses it

This docs site is one of those apps, with the render step moved to build time. `plugins/pele-diagrams.mjs`
calls `render()` on every `mermaid` fence, and the page ships the SVG. The browser only loads Pele's
zoom fragment when a diagram had to shrink. Details, config, and CSS wiring are in
[How this site renders Mermaid](#how-this-site-renders-mermaid).

Treat diagram text as untrusted if it comes from users - Pele escapes labels and filters links, but
you still validate input and show errors as text. See [Security](https://pele.run/security) and
[Treat diagram input as untrusted](#treat-diagram-input-as-untrusted) above.

## How this site renders Mermaid

Diagrams are drawn by [Pele](https://pele.run/), a Mermaid renderer that runs in Node. It draws during
the same pass as the rest of the site, so every page ships plain SVG:

- The diagram is in the HTML. Nothing has to run before it appears.
- The site does not install Mermaid at all.
- The color mode switches with CSS variables. A diagram does not redraw.
- A diagram that does not parse fails `pnpm build`.
- A diagram that had to shrink to fit its column gets pan and zoom. That fragment loads on demand, so a
  diagram that fits stays a plain SVG.

`plugins/pele-diagrams.mjs` renders each fence, and `src/theme/Mermaid` prints the SVG Docusaurus
produces for a `mermaid` code block. Two settings in `docusaurus.config.ts` wire it up:

```typescript
const config = {
    markdown: {
        // Off: plugins/pele-diagrams.mjs renders the fences itself.
        mermaid: false,
    },
    presets: [
        ['classic', {
            docs: {
                remarkPlugins: [peleDiagrams],
            },
        }],
    ],
};
```

The language has to be exactly `mermaid`. A title or a highlight range on the fence is ignored: the
block still renders, and the title does not appear.

Pele uses its own layout engine, and it covers every diagram type built into Mermaid 12.1. The colors
and fonts come from CSS, not from the diagram:

| Item | Value here |
|------|------------|
| Renderer | Pele, every Mermaid 12.1 diagram type |
| Labels | SVG text: line breaks, bold, and italic; other HTML is not supported |
| Colors | `--pele-*` variables, mapped to the Infima palette in `src/css/custom.css` |
| Color mode | Follows the theme toggle, without a re-render |
| `%%{init}%%` | Parsed, but `theme` and `themeVariables` do not apply |
| `click node "https://..."` | Rendered as a link; JavaScript callbacks are ignored |
| Sizing | The SVG scales down to the column |
| Zoom | Only for diagrams that had to shrink; see [Responsive diagrams](#responsive-diagrams) |

The root of every diagram is `<svg class="pele">`. Style a diagram, or one element of it, through the
variables and classes from the [Pele theming page](https://pele.run/theming):

```css
.pele {
    --pele-accent: var(--ifm-color-primary);
}

.pele-node[data-id="start"] .pele-label {
    fill: var(--pele-accent);
}
```

`classDef` fill and stroke colors are literal CSS. They do not follow the toggle. Prefer the theme
colors, and put the meaning in the label when color would otherwise be the only signal.

### Responsive diagrams

Wide diagrams are hard to read on a phone. Several focused diagrams beat one dense canvas. Use short
labels, and look at the page at a narrow width before you publish it. A diagram scales down to the
column, so a wide chart becomes unreadably small: split it instead.

A diagram that had to shrink gets zoom controls. Pele's zoom is a lazily loaded fragment, and it only
activates when a diagram is wider than its column: every other diagram stays a plain SVG with no
controls and no script.

| Input | Action |
|-------|--------|
| `+`, `-`, `0` | Zoom in, zoom out, and reset, with the diagram focused |
| Arrow keys | Pan, with the diagram focused |
| Pinch, or `Ctrl`/`Cmd` + wheel | Zoom at the pointer |
| Drag | Pan a zoomed diagram |
| Double-click | Zoom in, or reset |
| The three buttons | Zoom in, zoom out, and reset |

The wheel without a modifier key keeps scrolling the page. The controls take their colors from the
`--pele-*` variables above, and `--pele-zoom-top`, `--pele-zoom-right`, `--pele-zoom-bottom`, and
`--pele-zoom-left` move them.

Pele can also re-layout a diagram for the available width (`maxWidth`, `autoDirection`), but that runs in
the browser of every reader. This site draws once at build time and scales the result.
